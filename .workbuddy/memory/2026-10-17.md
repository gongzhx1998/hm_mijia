## 修复 signedPost "unsupported characters" 报错

根因：登录走 WebView 路径时 `completeLoginWithToken` 只设置 serviceToken/userId，未设置 ssecurity。
ssecurity 是 RC4 签名密钥来源，为空时 `genSignedNonce('')` → `base64Decode('')` → `decodeSync('')` 抛
"The input string contains unsupported characters"。

修复：
1. `completeLoginWithToken` 补取 ssecurity（ssecurity 空时调用 `fetchSsecurityAfterVerify`）。
2. `signedPost` 里 ssecurity 为空时直接抛清晰错误，不再静默生成错误签名。
3. `MiCrypto.base64Decode` 增强防御：清洗非法字符 + 空串返回空字节 + 按 4 对齐补 padding，
   彻底避免 decodeSync 抛 unsupported characters。
4. 关键日志（请求 url/明文 data/ssecurity/响应码/响应体原文/解密后 body）全部改用 error 级别，
   因为鸿蒙 console.info 默认不落盘，看不到关键信息。

后续验证：重编后看日志 `>>> signedPost 请求 url=...` 和 `>>> ssecurity_len=...`；
若 ssecurity_len=0 说明登录态仍不完整，需看 completeLoginWithToken 是否成功补取 ssecurity。

## 修复 auth error（RespCode:401 + {"code":2,"message":"auth error"}）

现象：ssecurity 已拿到（24字符），但云接口返回明文 auth error（非 RC4 密文），说明 HTTP 层鉴权失败。

根因排查（对照 hass-xiaomi-miot + cuckoo711/mijiaAPI_V2 SDK 源码）：
1. **serviceToken 签发缺 clientSign**（核心）：小米协议里 step3 拿 serviceToken 必须
   `GET location&clientSign=<urlencode(base64(sha1("nonce=<登录nonce>&<ssecurity>")))>`，
   之前直接 GET location，拿到的 serviceToken 无效。登录 nonce 是 serviceLoginAuth2 响应的 nonce 字段
   （不是请求签名的 genNonce）。
2. **Header 字段名应全小写连字符**：`miot-encrypt-algorithm`/`miot-accept-encoding`/`accept-encoding`/`x-xiaomi-protocal-flag-cli`，
   之前用大写 `MIOT-ENCRYPT-ALGORITHM`，且缺 `miot-accept-encoding: GZIP`。
3. **Cookie 缺 PassportDeviceId**，且标准结构是 `cUserId + yetAnotherServiceToken + serviceToken + PassportDeviceId`
   （不需要 locale/timezone/channel 等多余字段）。

修复：
1. 新增 `loginNonce` 模块变量，保存 serviceLoginAuth2 响应的 nonce。
2. 新增 `fetchServiceToken(location)`：拼 clientSign 后 GET，替换 login/completeLoginAfterVerify 里所有
   直接 GET location 的调用。
3. signedPost 的 header 改全小写连字符 + 补 miot-accept-encoding，Cookie 改标准结构。
4. 新增持久化：`persistSession`/`restoreSession`/`clearSession`，登录成功各分支调用 persistSession，
   Home.aboutToAppear 调用 restoreSession。避免 App 重启后 ssecurity/serviceToken 丢失导致 auth error。
5. 关键日志全改 error 级别（请求 url/data/ssecurity/serviceToken/Cookie/响应码/响应体/解密后 body）。

验证要点：重编后看 `>>> fetchServiceToken 拼 clientSign` 日志确认 clientSign 生效；
若仍 auth error，看 `>>> serviceToken=...` 完整值是否有效，以及 `>>> replay serviceLoginAuth2 body=` 里
nonce/ssecurity/location 是否都拿到。

## 修正：sid=xiaomiio 不需要 clientSign

现象：加了 clientSign 后，sts 返回 200 + body "ok"，但 cookieJar 里没有 serviceToken，登录失败。

根因（对照 hass-xiaomi-miot xiaomi_cloud.py 源码）：
```python
if self.sid != 'xiaomiio':   # 只有 sid != xiaomiio 才拼 clientSign
    sign = f'nonce={auth.get("nonce")}&{auth.get("ssecurity")}'
    ...
    location += '&clientSign=' + parse.quote(sign)
```
**sid=xiaomiio 时直接 GET location 拿 serviceToken，不能拼 clientSign**。之前拼 clientSign 反而导致
sts 返回 200 "ok" 但签发不出 serviceToken。已撤销 clientSign 逻辑（删除 loginNonce 变量、
fetchServiceToken 改回直接 GET location）。

当前待验证：撤销 clientSign 后，sts 应正常返回 Set-Cookie: serviceToken。
已加诊断日志：httpGetFollowRedirect 里遍历打印所有含 cookie/location 的响应 header
（`>>> step3 header[xxx]=yyy`），确认 serviceToken 到底在哪个 header。
getHeaderValue 增强：header 值为数组（多个 Set-Cookie）时 join('\n')。

关键结论（长期有效）：
- sid=xiaomiio（米家 MIoT）：登录三步 = GET serviceLogin → POST serviceLoginAuth2 → 直接 GET location，
  无需 clientSign。
- clientSign 仅 sid != xiaomiio（micoapi/mina/miothealth 等）才需要。

## 定位 auth error 真正根因：ssecurity 来源错误（无效值）

决定性验证：用 Python 标准库，用日志里的真实 ssecurity/serviceToken，严格按参考实现算法，
请求 api.mijia.tech 和 api.io.mi.com **两个域名都返回 401 + auth error**。
→ 证明不是 ArkTS 签名算法问题，而是**凭证本身无效**。

根因：ssecurity 拿到了「错误来源的值」。
- 正确来源：`POST /pass/serviceLoginAuth2` 响应的 `ssecurity` 字段（唯一正确）。
- 错误来源：`GET /pass/serviceLogin?sid=xiaomiio` 返回的 `ssecurity`（占位/无效值）。
- 之前的 `fetchSsecurityAfterVerify` 和 `completeLoginAfterVerify` 方式2 都从 GET serviceLogin 拿 ssecurity，
  拿到无效值并持久化，导致云签名 401 auth error。

修复：
1. 新增 `replayAuth2ForSsecurity()`：重放 serviceLoginAuth2（用 pendingUser/pendingHash/pendingSign/qs/callback）
   拿正确 ssecurity。`fetchSsecurityAfterVerify` 优先走重放，GET serviceLogin 仅作兜底。
2. `completeLoginAfterVerify` 方式2 不再从 GET serviceLogin 拿 ssecurity（只拿 userId/passToken/location），
   ssecurity 统一走方式3重放。
3. `signedPost` 遇 code=2（auth error）时自动重放 auth2 刷新 ssecurity 并重试一次（authRetried 防递归）。
4. `persistSession`/`restoreSession` 增加 pendingUser/pendingHash/pendingSign/qs/callback 持久化，
   跨 App 重启也能重放 auth2 刷新无效 ssecurity。
5. Cookie 补全 timezone_id/timezone/is_daylight/dst_offset/locale 字段。

用户需重新登录一次让新逻辑生效（当前已恢复的 ssecurity 是旧的无效值，且旧版本未持久化 pending 参数，
无法自动重放，只能重新登录）。

关键结论（长期有效）：
- **ssecurity 只能从 serviceLoginAuth2（POST）响应拿，GET serviceLogin 返回的 ssecurity 是无效值**。
- 参考实现：Do1e/mijia-api（Python，api.io.mi.com，sid=xiaomiio）与 CodeByZack/mijia-api
  （mijia-node，api.mijia.tech，sid=mijia）—— 大陆 api.mijia.tech 用 sid=xiaomiio（逆向确认）。
- 签名算法、RC4、nonce 格式均与参考实现逐字节一致（已用 Python 验证签名输出）。

## 决定性逆向：clientSign 是必需的 + serviceToken 从 header 拿（纠正上一节错误结论）

用 jadx 1.5.3 CLI + `--show-bad-code` 重新反编译 aa.apk，拿到 mje.OooO0oo（RC4 加密）的完整 smali，
以及 XMPassport.getServiceTokenByStsUrl / getClientSign / Coder.generateSignature 源码，确认：

**上一节"sid=xiaomiio 不需要 clientSign"的结论是【错误的】**（hass-xiaomi-miot 的 sid!=xiaomiio 判断不适用 aa.apk）。

真实流程（XMPassport.java:797 + 642 + 1148 + 1195）：
1. `serviceLoginAuth2` 响应含 `nonce`（Long 数字）、`ssecurity`、`location` 三个字段。
2. `clientSign = Coder.generateSignature(null, null, {nonce: nonce}, ssecurity)`
   = `base64(SHA1("nonce=<nonce>&<ssecurity>"))`（无 method/path，TreeMap 只有 nonce 一项）。
3. `GET <location>?clientSign=<urlencode(clientSign)>&_userIdNeedEncrypt=true`。
4. **serviceToken 从响应 header `xiaomiio_serviceToken`（sid+_serviceToken）拿，失败再找 `serviceToken`，
   不是从 Set-Cookie 拿！**（`asString.getHeader(str + "_serviceToken")`，str=serviceId=xiaomiio）。

RC4 加密算法（mje.OooO0oo smali，与之前结论一致，已验证）：
- nonce = m52.OooO00o(timeDiff) = base64(8字节SecureRandom + writeInt((now+timeDiff)/60000)大端4字节)
- signedNonce = base64(SHA256(b64decode(ssecurity) ++ b64decode(nonce)))
- RC4 key = b64decode(signedNonce)（必须 32 字节，e3a 构造校验）
- rc4_hash__ = m52.OooO0O0("POST", path, {data明文}, signedNonce)（path=netRequest.OooOo0O="/v2/..." 不含/app）
- 签名串 = [METHOD.toUpperCase, Uri.parse(path).getEncodedPath, TreeMap排序的k=v, signedNonce] join("&") → SHA1 → base64
- data/rc4_hash__ 各自 RC4(key, drop1024) 加密 → signature = 同上签名（用密文）
- 表单键序：data, rc4_hash__, signature, _nonce, ssecurity

本轮修复：
1. 恢复 loginNonce（保存 serviceLoginAuth2 的 nonce，之前误删）。
2. fetchServiceToken 拼 clientSign + `_userIdNeedEncrypt=true`。
3. serviceToken 从 header xiaomiio_serviceToken/serviceToken 拿（HttpTextResult 加 headers 字段，
   httpRaw/httpGetFollowRedirect 填充，新增 respHeaderToMap/findHeaderValue）。
4. login/replayAuth2ForSsecurity/completeLoginAfterVerify 各分支统一保存 nonce + 三级兜底取 serviceToken
   （header xiaomiio_serviceToken → header serviceToken → cookie）。

域名/接口确认真实（DeviceApi.java:1319 + MijiaCookie.java:55）：
- 域名 api.mijia.tech（ir7.OooOo: CN → "https://" + str + "api.mijia.tech"，str=null→空）
- 设备列表 /v2/home/device_list_page（Crypto.RC4）
- mico 通道（SmartHomeRc4Manager）：/homeroom/gethome、/home/device_list（另一套，暂不用）
- iOS 抓包看不到 device_list_page 是因为 iOS 版用 mico.api.mijia.tech + OAuth2 + AES/RSA（新协议），
  与 Android aa.apk 的 api.mijia.tech + RC4 不同。aa.apk 无 mico.api.mijia.tech/X-Encrypt-Type 痕迹，仍是 RC4。

## 决定性根因：鸿蒙 http 组件自动跟随重定向导致 serviceToken 丢失（改用 rcp）

现象：step3 `GET location` 返回 200 + body "ok"，但 respCookies 空、header 无 xiaomiio_serviceToken，
登录仍拿不到 serviceToken。日志 `step3 hop=0 code=200` 只有一跳（应为多跳 302 重定向链）。

根因（官方文档 + 论坛确认）：
- 鸿蒙 @ohos.net.http 的 `request()` **会自动跟随 302 重定向且无法禁用**（官方论坛原话：
  「http 不支持禁止重定向，建议使用 rcp 模块接口实现」）。
- sts 签发 serviceToken 靠重定向链中间的 Set-Cookie 写入，http 底层自动跟随后把这些中间
  Set-Cookie 丢弃，最终只返回 200 "ok" + 空 Cookie，导致 serviceToken 拿不到。

修复（MiCloud.ets 的 httpGetFollowRedirect 改用 rcp）：
- `import { rcp } from '@kit.RemoteCommunicationKit'`。
- rcp.createSession({ requestConfiguration: { transfer: { autoRedirect: false, timeout: {...} } } })。
- 用 `session.fetch(new rcp.Request(url, 'GET', headers))` 手动逐跳跟随 Location，每跳累积 Set-Cookie 进 cookieJar。
- rcp Response 类型要点：`headers` 是 `ResponseHeaders`（索引签名 `[k:string]: string|string[]|undefined`），
  值可能是数组（多个 set-cookie）；`cookies` 是 `ResponseCookie[]`（{name,value}，非对象）；`toString()` 返回 string|null；
  `statusCode` 是 number；`Session.close()` 是 void（不是 Promise）。
- 请求头用 rcp.RequestHeaders 类型 + 小写键（'user-agent'/'content-type'/'cookie'）。

关键结论（长期有效）：
- **鸿蒙 http 组件不能用于需要手动控制重定向的登录/鉴权流程**，一律用 rcp + autoRedirect:false。
- serviceToken 仍从重定向链 Set-Cookie 拿（文档 4.2 节第3步明确：GET location 跟随 302 → Set-Cookie serviceToken/userId/cUserId/passToken），
  不是 header 也不是 location 的 auth 参数。location 里的 auth= 是 RSA 加密的 token，sts 用它解密后 Set-Cookie。

## 【决定性修正】clientSign 是错误方向：大陆 sid 直接 GET location 无 clientSign，serviceToken 从 Set-Cookie 拿

上一节及更早的「clientSign 必需 + serviceToken 从 header xiaomiio_serviceToken 拿」是【错误结论】，
导致 sts 校验 clientSign 失败静默返回 200 "ok" 却不签发 serviceToken，登录一直失败。

正确流程（对照可工作的第三方库 yaomaolei/mijia-api + Do1e/mijia-api 源码）：
1. sid：大陆用 xiaomiio 或 mijia 均可（yaomaolei 用 xiaomiio、Do1e 用 mijia 都能工作；
   aa.apk 逆向 ir7.java 第487行 `OooOoOO()`：st→mijia-test，海外→xiaomiio，大陆CN→mijia）。
2. 登录三步：GET serviceLogin → POST serviceLoginAuth2（sid/user/hash=MD5(pwd)大写/_sign/qs/callback）
   → **直接 GET location，无 clientSign、无 _userIdNeedEncrypt**。
3. **serviceToken 从 sts 重定向链的 Set-Cookie 拿**（requests.session.get(location) → cookies['serviceToken']），
   不是 header，也不是 location 的 auth 参数。
4. hash 算法 = MD5(password) 十六进制大写（yaomaolei：`(md5(pwd).hexdigest().upper() + '0'*32)[:32]`，即 MD5 大写本身）。

XMPassport.getServiceTokenByStsUrl 里带 clientSign + 从 header 拿 token 是【海外 sid 的 XMPassport 流程】，
大陆 sid=xiaomiio/mijia 走的是更简单的直接 GET location + Set-Cookie 流程。

本轮修复（MiCloud.ets）：
1. `fetchServiceToken`：删掉 clientSign 拼接，直接 GET location。
2. 新增 `extractServiceToken(step3)`：优先 cookieJar（累积所有跳 Set-Cookie）→ 最后一跳 cookies → header 兜底，
   统一替换所有 serviceToken 读取点（之前都是 header 优先，错）。
3. 保留上一轮的 rcp autoRedirect:false 手动跟随重定向（这个是对的，http 组件会丢中间 Set-Cookie）。

## 附带发现：JS 大整数精度丢失（nonce 19 位 Long）

serviceLoginAuth2 响应的 nonce 是 19 位 Long（如 8082866328074280000），远超 JS 安全整数 2^53≈9e15。
JSON.parse 会把它转 double 丢精度（8082866328074280000 → 8082866328074279936，差 64）。
`String(double)` 的 round-trip 不保证无损（9 个测试值 5 个 FAIL，如 1234567890123456789 → 1234567890123456800）。
修复：新增 `extractNonceString(text)` 用正则从原始 JSON 文本提取 nonce 字符串，绕过 JSON.parse。
（注：nonce 现在不再用于 clientSign，但保留提取逻辑无害，未来若再需要签名时可用。）

## 【最终根因】sid 与域名错配：sid=xiaomiio（海外）+ api.mijia.tech（大陆）→ 401 auth error

上一节"大陆用 xiaomiio 或 mijia 均可"是【错的】。登录已能拿到 serviceToken，但请求
api.mijia.tech 仍 401 `{"code":2,"message":"auth error"}`（明文，服务器在 RC4 解密前就拒了）。

决定性证据（三方一致）：
1. aa.apk 反编译 ir7.java 第532行 `OooOoo0()`：`return d98.OoooO(serverBean) ? "xiaomiio" : "mijia"`，
   第487行 `OooOoOO()` 同逻辑；`d98.OoooO()`：serverBean==null/CN/st → false，海外 → true。

## 【协议升级】RC4 已弃用，api.mijia.tech 改用 AES（ENCRYPT-AES + aes_hash__）

sid 改对后仍 401。用户用 iOS 抓包发现 iOS 11.8.204 用的是【AES】协议，不是 RC4：
- 请求头 `miot-encrypt-algorithm: ENCRYPT-AES`（不是 ENCRYPT-RC4）
- body 字段 `aes_hash__`（不是 rc4_hash__），且【无 ssecurity 字段】
- 多了 `miot-origin-request-version` / `domain-refer` / `origin-from` / `operate-common` 等 header

验证：Python 复现用户抓的 AES 请求 → 200（响应是 AES 密文 base64）；而 ArkTS 的 RC4 请求 → 401 auth error。
→ 结论：api.mijia.tech 已弃用 RC4，必须换 AES。这解释了为什么签名算法逐行核对无误仍 401。

解码抓包数据：
- `_nonce` = ffffffffbba4ec72 01c7c7f4（12字节 = 8随机 + 4分钟时间戳，格式同 RC4）
- `aes_hash__` = 8b46e3bd1efef36b7d1cd5bf（12字节）
- `signature` = 98ab46cf...86a8e0（20字节 = SHA1）
- `data` = 79字节（不是16倍数 → 非 CBC-PKCS7，是 CTR/GCM/CTS 等流式模式）

旧 aa.apk 反编译 `Crypto.java` 枚举只有 NONE/RC4/HTTPS，无 AES；全库无 aes_hash__/ENCRYPT-AES。
Do1e(v5.0.0 Oct2026)/hass-xiaomi-miot/micloud 全都还是 RC4，【AES 算法无人开源，需逆向】。

待逆向（关键未知）：
1. AES key/IV 推导（大概率仍从 signed_nonce=base64(sha256(ssecurity||nonce)) 派生，但具体取前16/后16/MD5 未知）
2. aes_hash__（12字节）如何计算
3. signature 的签名串结构（大概率仍 SHA1("POST&path&data=x&aes_hash__=x&signed_nonce")）
4. AES 模式（CBC/CTR/GCM/CTS，data 79字节非16倍数排除 CBC-PKCS7）

下一步需要：iOS 端 ssecurity（抓 iOS 登录 serviceLoginAuth2 响应的明文 ssecurity）来验证 key 推导，
或新版 Android 米家 APK（11.x，含 AES 代码）反编译找实现。

## 【突破】AES 算法已从 11.8.705 反编译出来并实现到 ArkTS

用户提供新版 APK `米家_11.8.705.apk`（239MB，12个 dex）。反编译工具：jadx 1.5.6-all.jar，
需 JDK 17（`D:/Java/jdk-17.0.2/bin/java.exe`，系统默认 Java 8 会报 UnsupportedClassVersionError）。

定位：`ENCRYPT-AES`/`aes_hash__` 字符串在 **classes10.dex**（grep 二进制 dex 定位）。单独反编译 classes10.dex：
`java -cp jadx-gui-1.5.6-all.jar jadx.cli.JadxCLI -d cls10_out --no-res dex/classes10.dex`。

关键类（混淆名）：
- `_m_j/vd.java`（AES 加密主逻辑，OooOO0=加密/OooO0oo=解密）
- `_m_j/vr2.java`（OooO00o=nonce生成/OooO0O0=signature计算）
- `_m_j/x4d.java`（OooO0oO=concat字节数组）在 classes9.dex
- `_m_j/zba.java`（Oooooo0=SHA256）
- `_m_j/ud.java`（EncryptContext: iv+key）

AES 算法完整流程（已 100% 确认）：
1. nonce = base64(8随机 + 4分钟时间戳)（同 RC4，vr2.OooO00o 用 writeLong+writeInt）
2. signed_nonce = base64(SHA256(base64decode(ssecurity) ‖ base64decode(nonce)))（同 RC4）
3. AES key = base64decode(signed_nonce) = 32字节；AES IV = 12字节随机（SecureRandom）
4. 每个参数独立 AES-256-GCM（Cipher.getInstance("AES/GCM/NoPadding") + GCMParameterSpec(128, iv)），同 key+iv
5. **aes_hash__ = base64(iv)**（就是 GCM 的 12 字节 IV，不是 hash！）
6. signature = base64(SHA1("POST&path&aes_hash__=xxx&data=xxx&signed_nonce"))，参数 **TreeMap 字典序**（aes_hash__ 在 data 前）
7. 请求体 {data, aes_hash__, signature, _nonce}，**无 ssecurity**

根因 & 修复：
1. **UDP 竞态（主因）**：`MiioClient.rawSend` 原先是 `await send()` 之后才 `on('message')`，局域网毫秒级响应在监听注册前到达被丢 → 3 秒超时。修复：**先注册 message 监听再 send**。

3. **控制无回退**：局域网失败直接抛错。修复：局域网失败回退云端 rpc；且 rpc 检查 `error` 字段（不止顶层 code）。
4. **设备类型识别太糙**：`deviceTypeFromModel` 只 substring 匹配，`xiaomi.airp.mp4`/`lumi.acpartner.mcn02`/`xlang.desk.vlocv2` 全漏判 → 图标📱+详情页无控制面板。修复：`CloudDevice` 加 `specType` 字段（解析 `spec_type`），`deviceTypeFromModel` 优先用 spec_type 类别（urn:miot-spec-v2:device:<类别>:...），回退 model 的 category 段（vendor.category.model 的中间段）；新增 air_purifier/humidifier/desk/fan/heater/curtain/lock/washer/fridge/router 类型。
5. `Home.deviceIcon` + `isSwitchable` 补新类型；`DeviceControl` 详情页为 air_purifier/humidifier/fan/heater/desk 加电源开关分支。
6. 防御：旧缓存 CloudDevice 无 specType → `cd.specType ?? ''`。

关键教训：**miIO 局域网控制 UDP 必须先 on('message') 再 send**；**set_power 参数是字符串 'on'/'off' 不是 boolean**；**米家云 rpc 响应的真实错误在 error 字段，不在顶层 code**；**设备类型识别必须用 spec_type/model 的 category 段，不能 substring**。

## spec 驱动动态渲染（15:29）
用户要求详情页真实控制（之前只有名称，控制是硬编码的电源开关）。

逆向确认 spec 定义获取接口（关键）：
- `POST /appgateway/gspec/Gspec/get_instances_by_dids`（挂在 api.mijia.tech 下，完整 URL = `https://api.mijia.tech/app/appgateway/gspec/Gspec/get_instances_by_dids`）
- 请求 data：`{"dids":[...],"urns":["",...],"isGetFullInstance":true}`
- 响应：`instances[did] = {urn, isSpecv3, instance}`，`instance` 是 spec JSON 字符串
- spec 结构：`{type: urn, services: [{iid(siid), type, properties: [{iid(piid), description, format, access:[read/write/notify], unit, value-range:[min,max,step]}]}]}`

关键结论：**设备可操控动作由服务端下发的 miot-spec 定义决定**（米家 App 用 SpecCard 动态渲染）。
- format=bool → 开关；format=数值+value-range → 滑块（min/max/step 由 spec 决定）
- 电源通用 siid=2/piid=1；亮度 siid=2/piid=2；模式 siid=2/piid=3（台灯实测）

实现：
1. MiCloud.ets 新增 `SpecProperty`/`DeviceSpec` 接口 + `getDeviceSpecs(dids)`（拉取+解析 spec，只保留可写属性）+ `miotGetPropValues(did, siids, piids)`（批量读值，key=`${siid}.${piid}`）。
2. DeviceControl.ets 重写为 spec 驱动：aboutToAppear 拉 spec + 批量读值；`SpecPropControl` 动态渲染（bool→Toggle，数值+range→Slider）；Slider 用 SliderChangeMode.Moving 只更新本地、End/Click 才下发 miotSetProp（避免拖动狂发请求）；写值用 miotSetProp(siid/piid/value)。
3. Home.ets 首页快速开关仍走 controlDevice（set_power→siid=2/piid=1）。

关键教训：**spec 定义的 services[i].iid 是 siid、properties[j].iid 是 piid**；**value-range 是 [min,max,step] 三元组**；**access 数组含 'write' 才是可写**；**instance 字段是 JSON 字符串需二次 parse**。
