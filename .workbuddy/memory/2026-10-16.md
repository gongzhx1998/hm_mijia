## 二次验证"获取登录态失败"根因彻底定位（GitHub 逆向）

- 查证了 micloud(Squachen)、hass-xiaomi-miot(al-one)、go-micloud(wangbjun)、MiUnlockTool(offici5l)、mi-gpt(idootop) 五个开源实现。
- **真正根因：鸿蒙 http 模块默认不自动跟随 302 重定向**（targetSDK≥12 禁止自动跟随）。小米登录 step3 的 serviceToken 是通过 GET location 的重定向链 Set-Cookie 写入的，之前 httpRaw 不跟随重定向，所以拿不到 serviceToken。
- 关键事实（对照 micloud/hass-xiaomi-miot）：
  - ssecurity/passToken/userId/cUserId/nonce 都在 serviceLoginAuth2 的 **响应 body** 里（sid=xiaomiio 时）。
  - serviceToken 在 GET location 的响应 Set-Cookie 里，需跟随重定向链（go-micloud 的 passServiceLogin 连续跟随 4 次 Location header）。
  - 二次验证通过后，重新 GET /pass/serviceLogin 会 code=0 且 body 带 ssecurity（hass-xiaomi-miot _login_step1 是 ssecurity 唯一来源）。
  - 登录前需设 pass_ua=web cookie（go-micloud）。
  - callback 写死 https://sts.api.io.mi.com/sts，qs 写死 %3Fsid%3Dxiaomiio%26_json%3Dtrue。
- 修复：MiCloud.ets 新增 httpGetFollowRedirect（手动跟随 Location 最多10跳，每跳用 buildCookieHeader 累积 Set-Cookie 到 cookieJar）；login 的 step3、completeLoginAfterVerify 的所有 GET location 改用 httpGetFollowRedirect；login 增加 pass_ua=web cookie；completeLoginAfterVerify 增加"重新 GET serviceLogin 拿 ssecurity"分支（gotSsecurity 标记）；getHeaderValue 解析 Location header。
- 若仍失败，看日志：`step1 after verify code=...`、`replay serviceLoginAuth2 code=...`、`gotSsecurity=...`、`Login] onVerifyIntercept url=...`、`account cookie=...`、`sts cookie=...`。

  - signature = base64(sha1("POST&" + path + "&k=v..." + "&signed_nonce"))，path=去掉/app/的路径。
  - 响应 RC4 解密（用发送的 _nonce 派生 signed_nonce）。
  - 设备列表参数应为 {"getVirtualModel":true,"getHuamiDevices":1,"get_split_device":false,"support_smart_home":true}。
  - 家庭接口应为 /v2/homeroom/gethome_merged，参数 {fg:true,fetch_share:true,fetch_share_dev:true,fetch_cariot:true,limit:300,app_ver:7,plat_form:0}。

## 修复 gethome_merged "unsupported characters" 崩溃（10:03）
- 报错：signedPost /v2/homeroom/gethome_merged http error: The input string contains unsupported characters
- 根因：鸿蒙 util.Base64Helper.decodeSync 对含杂质的 base64（ssecurity 含空白/换行，或响应体非 RC4 密文而是明文错误/HTML）抛 "unsupported characters"，被 signedPost 的 catch 吞成 http error
- 修复（MiCloud.ets）：
  1. 新增 cleanBase64()：base64 解码前剔除非法字符，genSignedNonce/rc4Encrypt/rc4Decrypt 的 key 解码全部套用
  2. 新增 isValidBase64()：rc4DecryptStr 解密前校验响应体，非 base64（明文错误）直接返回原文，日志能看到服务器真实错误码
  3. signedPost 增加 ssecurity/nonce/url 详细日志
  4. 新增 fetchSsecurityAfterVerify()：二次验证方式1/1.5 拿到 serviceToken 但 ssecurity 为空时，补 GET serviceLogin 拿 ssecurity（ssecurity 是签名必需）
- 待用户重编译验证：若仍失败，看日志 ssecurity_len= 和 rc4DecryptStr 响应体，能定位是签名错还是 ssecurity 缺失
